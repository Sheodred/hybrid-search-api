# ADR-0003: Upgrade to Elasticsearch 9.5.2, keeping the in-process RRF implementation

## Context

The stack ran `elasticsearch:8.14.1` with the Python client pinned
`elasticsearch>=8.13,<9`. For a portfolio project aimed at Elasticsearch
specialist roles, running a nearly two-major-versions-old server is the wrong
signal, and the planned rich-index/query work assumes a GA `retriever` API.

An audit of every Elasticsearch call site found almost nothing to migrate:
the removed `body=` parameter is not used anywhere (`ensure_index` uses
`settings=`/`mappings=`, search uses `query=`/`knn=`/`from_=`/`size=`, seeding
uses `document=`), `build_client()` passes none of the constructor arguments
dropped in client 9.0, and the project builds raw query dicts rather than
using `elasticsearch_dsl`. The 8.x kwargs migration had already been done.

The upgrade was originally specced to also replace the hand-rolled
`_reciprocal_rank_fusion()` with Elasticsearch's native `rrf` retriever. That
part did not survive contact with the running server - see below.

## Decision

1. **Image and client pin move together**:
   `docker.elastic.co/elasticsearch/elasticsearch:9.5.2` and
   `elasticsearch>=9,<10`. The 9.x Python client supports only 9.x/10.x
   servers, so pinning one without the other produces an unsupported
   combination.
2. **The `esdata` volume is destroyed, not migrated** (`docker compose down -v`).
   ES 9.x will not start on an 8.14-created data path, and the contents are
   throwaway demo documents that `scripts/seed_data.py` recreates in seconds.
   A rolling 8.14 -> 8.18 -> 9.x upgrade would be pure ceremony here.
3. **`"index": true` is dropped from the `embedding` mapping** - it is the
   default in 9.x. `similarity: cosine` also defaults, but stays explicit: it
   decides how vectors are compared, which is worth reading straight off the
   mapping.
4. **`_reciprocal_rank_fusion()` stays.** The native `rrf` retriever is not
   available on this stack - see the next section.
5. `xpack.security.enabled=false` remains, and is still accepted as a dev
   override by the 9.5 image. This is a deliberate choice for a local
   demo stack only; a production deployment would enable security, put TLS in
   front of the cluster, and authenticate the API's client.

## Why not the native `rrf` retriever

The spec assumed the `rrf` retriever had moved to the free tier. Verified
against the running 9.5.2 container, it has not:

```
POST /<index>/_search  {"retriever": {"rrf": {...}}}
-> 403 security_exception
   "current license is non-compliant for [Reciprocal Rank Fusion (RRF)]"
```

| Retriever on a `basic` license | Available |
| --- | --- |
| `standard` | Yes |
| `knn` | Yes |
| `rrf` | **No** - 403 |
| `linear` | **No** - 403 |

So the fusion retrievers - exactly the ones that would replace our code - are
the licensed ones. The options were a 30-day trial license (expires, and must
be re-triggered after every `down -v`, so the demo would stop working for
whoever clones the repo), a try/except dual path (reintroduces the
two-implementation complexity the upgrade was meant to remove, with the
native branch never taken locally), or keeping the current implementation.

**Decision: keep the in-process implementation.** RRF is nine lines of
arithmetic - `score(doc) = Σ 1/(k + rank)` over both ranked lists, `k = 60`
from Cormack et al. (2009). What Elastic licenses is executing it server-side,
not the idea. Keeping it means `docker compose up` works on the free stack for
anyone who clones this repo, and the fusion logic stays readable in
`search/hybrid_search.py` instead of disappearing into a request body.

The trade-off accepted: two search round-trips instead of one, and fusion over
the two already-truncated `size`-length lists rather than over a larger
`rank_window_size` candidate pool. At demo-corpus scale neither is
measurable; at production scale with a paid license, the native retriever
would be the right move.

## Consequences

- `search/hybrid_search.py`, `search/queries.py` and their tests are unchanged
  by this upgrade - the audit found no 9.x incompatibility in them, and the
  retriever swap was dropped.
- `docs/search/index_settings.json` was regenerated by
  `tests/test_config_snapshots.py` after the mapping change.
- Verified on 9.5.2 after a clean reseed: `/health/elasticsearch` reports the
  cluster, `/index` shows the mapping with `document_count == 10`, and
  `/search` returns sanely ranked hits with RRF scores.
- Worth knowing for the next mapping change: at 384 dimensions, 9.5.2 defaults
  `dense_vector` to `index_options.type: bbq_hnsw` (binary quantization with
  rescoring), not `int8_hnsw` - that default is dimension-dependent. Nothing
  in this project relies on it, but it is what the live mapping now shows.
- Revisit if: this project ever runs against a licensed cluster, or Elastic
  moves the fusion retrievers to the free tier - at that point
  `_reciprocal_rank_fusion()` should be deleted in favour of the native
  retriever.
